# Phase15 C03 — opt-in push implementation

The provider is disabled by default. Test servers explicitly select `mock`; that mode is refused in production. No real Google credential exchange, registration or delivery was executed. Owner activation and phone/APNs delivery remain O09/O07/O08, with exact setup in [PUSH_NOTIFICATIONS_UZ.md](PUSH_NOTIFICATIONS_UZ.md).

The HTTP v1 adapter signs short-lived RS256 OAuth assertions, caches access tokens and coalesces refreshes, uses only fixed Google HTTPS endpoints, classifies retries without returning provider details, and revokes only explicit UNREGISTERED responses. Device tokens are encrypted with AES-256-GCM; account authentication plus a separate installation proof is required for rotation/account reassignment/revocation. Tokens and proofs never appear in list/status responses. Each account has a ten-active-device bound.

An SQLite outbox snapshots account, token hash and announcement revision; scheduled delivery rechecks consent, promotion opt-in, active/revision/expiry and a 90-day device TTL. Lease fencing, five-attempt retry/backoff, stable tag/collapse keys and idempotent enqueue survive worker restart. Ambiguous delivery failures remain **at least once**, not a claim of exactly-once push delivery. Logout drains/invalidates pending client registration and revokes all account devices server-side; cleanup has a bounded wait so an unresponsive permission dialog cannot trap account logout. Offline opt-out intent persists for retry.

The lazy native/web SDK adapter requests user permission; native auto-init starts disabled and an app-owned privacy bridge disables it again and awaits token deletion on opt-out. Web reuses the offline service worker, bounds notification text and opens only the app root. Foreground messages refresh in-app announcements. Admin has an explicit send button separate from publishing the in-app fallback, and clearly labels mock delivery.
