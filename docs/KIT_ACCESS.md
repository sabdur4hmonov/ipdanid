# Kit access and offline build credits

## Phase16 inventory update (2026-10-27)

The current fresh default is **3 full builds**, not the historical Phase5 four-build policy described below. Stored legacy policies/grants retain their original terms. `server/kit-inventory.ts` adds an owner-only offline inventory lifecycle: staging codes cannot log in or redeem; only a complete ready inventory can. Public issuance remains capped at100. Account/batch/grant/unlock indexes avoid scanning a million code rows on ordinary login. `server/kit-export.ts` streams an AES-256-GCM authenticated export; the CLI verifies every exported HMAC against SQLite before activation, then exercises real three-build entitlements in a rolled-back transaction. The private fresh database is a deployment bundle, not an automatic migration into an existing customer database. No million-concurrent-user load claim is made. Printing/deployment/key handling: [KIT_MILLION_UZ.md](KIT_MILLION_UZ.md). Phase16 server-protected generation is tracked separately; this inventory milestone alone does not change the local sequence visibility boundary.

Server core milestone: `server/kit-store.ts`, a separate additive schema on CustomerStore. No existing guides, hash format, credit ledger, jobs or saved progress is rewritten. Kit code login is a bearer credential: possession opens the one account first assigned to that delivered code. New code redemption can explicitly attach to an authenticated account; replay returns the same grant, another account cannot claim it. Keep box codes private. Plaintext codes are returned only once when a batch is issued and never stored in the DB/audit log. A lost batch response is a409 with its deterministic batch ID in the admin list; revoke/reissue explicitly, do not silently create a second batch.

Defaults:4 builds/kit, no redemption expiry, no credit expiry, unlimited kit redemptions/account and no rolling build cap. Admin may set code validity days, credit days counted from first redemption, maximum kits/account, and builds per rolling period; account overrides are supported. `creditDays=30` means four credits usable within30days, not a recurring subscription/refill. Expired unused credits stop counting; already unlocked guides remain valid forever. Revoking a batch prevents new code logins/claims; it does not revoke prior perpetual receipts or granted credits. Individual account limits and usage are visible to authorized code staff.

Each authenticated `(account,sequenceHash)` unlock is unique. One transaction checks limits, consumes exactly one valid kit grant (earliest expiry first) or an existing legacy credit, inserts unlock/request identity and audit. Retries, new request IDs and additional devices cannot spend twice for that account/sequence. A reused request key for a different sequence fails409. Zero credits fail402; limits fail403. Kit credit buckets are separate from legacy gift/job reserves, so old job refunds and gift rules cannot corrupt expiring grants. Legacy purchased credits can still unlock a new build; new kit credits are used by the build-unlock route, not transferred through old gift/job products.

An Ed25519 signer is generated once and persisted in the existing protected DB. Public JWK has no private field. Signed payload binds version, account, exact sequence SHA-256, device ID, unlock ID and original issuance time; no expiry. Private key is never returned or logged. The receipt can be reissued for a new device without a second charge. Signer and original receipts survive API restart. Public-key trust must be pinned by the installed production application/deployment; local development client may pin the first same-origin key, refusing silent replacement. Key backup/rotation is a production operational requirement.

Endpoints: public `/builds/key`, rate-limited `/account/kit`; authenticated `/builds/account`, `/builds/unlock`, `/codes/redeem` supports both old and new codes. `/account/kit` only attaches to an existing session if `attach:true` is explicit; stale sessions cannot block ordinary code login. Admin `/admin/kits` read, `/policy`, `/limits`, `/batch`, `/revoke` mutations require the codes permission. Existing loopback-origin, write budgets and12/min account-guessing budget apply; code/account identifiers, no secrets, enter audit.

Verification: new memory DB tests cover four-credit defaults, one-account claim, retries/key binding, cross-device receipts, real signature, depletion, expiry/period limits/account override, legacy credit isolation and revocation. HTTP verifier uses fresh protected-path-checked disk DB and own4448 port, verifies restart/signature/key persistence, staff denial, rate budget and idempotency.38/38 HTTP checks pass; report under test-results/kit-http-BvFMXv. ## Client gating and compatibility

New application generation explicitly opts into `params.accessPolicy="kit-build/1"`. This field is included in the existing sequence payload/hash and optimizer/local-source binding; no old branch acquires it implicitly and no existing hash/progress is rewritten. Previously saved/imported guides without this new field remain grandfathered; old pending recovery also retains its original metadata. New guide imports retain the flag. Removing the flag without recomputing the entire payload hash fails integrity. A determined user can recompute it; this compatibility path is part of the documented deterrent boundary.

Free full optical preview/PNG, connection count, metres and estimated time remain available. Flagged saved guides show a localized kit login/unlock gate; player, confirmed steps, step list and PDF/TXT/JSON controls are not mounted until access is verified. Locked projects are excluded from the old cloud-upload UI. Signed unlocks are stored outside immutable guide data in backend-namespaced device Preferences/localStorage. Verification requires pinned public key, actual Ed25519 signature, account/hash/device binding and exact payload shape. It has no expiry and works after logout/offline. Wrong device/hash/account/signature/extra payload fail. The device checks crypto capability before charging; unsupported WebViews fail closed and require an updated browser/WebView rather than fake verification.

The development client pins the first same-origin public key and refuses silent replacement. A server key change cannot consume another credit. Production deployment must pre-pin/backup its trusted signer. Deleting device data loses cached receipts; sign in with the original kit/account and request that same sequence again without a second charge. Request identity is stable across retries. Simulated receipt-write quota failure after the server debit is recoverable by the same request with no double spend. Already paid guides use `/builds/archive` to sync to their account at no extra charge; the old reserved-job path refuses flagged guides and refunds that reservation.

Account screen supports kit-code login plus existing email accounts. Explicit kit attachment cannot switch to a different kit's account. Code staff can set default policy/account overrides, issue batches, view hashed codes/account usage/remaining credits and revoke a batch. Local printable HTML contains real40mm QR symbols with4-module quiet zones and a human-readable code; CSV contains the private code list. QR encodes the code as text, without an external URL/service or automatic login. Download/print once and keep it private; phone scanning/actual printing remain owner acceptance checks. The pinned MIT [node-qrcode](https://github.com/soldair/node-qrcode)1.5.4 encoder and dijkstrajs MIT notices are retained under public/licenses and offline cache; no remote QR generation. No printed-box production website is invented.

This is a client access deterrent, **not unbreakable DRM**: a local fitter necessarily has the sequence in memory/local library and determined users can modify it.
