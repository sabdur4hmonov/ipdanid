# Kit access and offline build credits

Server core milestone: `server/kit-store.ts`, a separate additive schema on CustomerStore. No existing guides, hash format, credit ledger, jobs or saved progress is rewritten. Kit code login is a bearer credential: possession opens the one account first assigned to that delivered code. New code redemption can explicitly attach to an authenticated account; replay returns the same grant, another account cannot claim it. Keep box codes private. Plaintext codes are returned only once when a batch is issued and never stored in the DB/audit log. A lost batch response is a409 with its deterministic batch ID in the admin list; revoke/reissue explicitly, do not silently create a second batch.

Defaults:4 builds/kit, no redemption expiry, no credit expiry, unlimited kit redemptions/account and no rolling build cap. Admin may set code validity days, credit days counted from first redemption, maximum kits/account, and builds per rolling period; account overrides are supported. `creditDays=30` means four credits usable within30days, not a recurring subscription/refill. Expired unused credits stop counting; already unlocked guides remain valid forever. Revoking a batch prevents new code logins/claims; it does not revoke prior perpetual receipts or granted credits. Individual account limits and usage are visible to authorized code staff.

Each authenticated `(account,sequenceHash)` unlock is unique. One transaction checks limits, consumes exactly one valid kit grant (earliest expiry first) or an existing legacy credit, inserts unlock/request identity and audit. Retries, new request IDs and additional devices cannot spend twice for that account/sequence. A reused request key for a different sequence fails409. Zero credits fail402; limits fail403. Kit credit buckets are separate from legacy gift/job reserves, so old job refunds and gift rules cannot corrupt expiring grants. Legacy purchased credits can still unlock a new build; new kit credits are used by the build-unlock route, not transferred through old gift/job products.

An Ed25519 signer is generated once and persisted in the existing protected DB. Public JWK has no private field. Signed payload binds version, account, exact sequence SHA-256, device ID, unlock ID and original issuance time; no expiry. Private key is never returned or logged. The receipt can be reissued for a new device without a second charge. Signer and original receipts survive API restart. Public-key trust must be pinned by the installed production application/deployment; local development client may pin the first same-origin key, refusing silent replacement. Key backup/rotation is a production operational requirement.

Endpoints: public `/builds/key`, rate-limited `/account/kit`; authenticated `/builds/account`, `/builds/unlock`, `/codes/redeem` supports both old and new codes. `/account/kit` only attaches to an existing session if `attach:true` is explicit; stale sessions cannot block ordinary code login. Admin `/admin/kits` read, `/policy`, `/limits`, `/batch`, `/revoke` mutations require the codes permission. Existing loopback-origin, write budgets and12/min account-guessing budget apply; code/account identifiers, no secrets, enter audit.

Verification: new memory DB tests cover four-credit defaults, one-account claim, retries/key binding, cross-device receipts, real signature, depletion, expiry/period limits/account override, legacy credit isolation and revocation. HTTP verifier uses fresh protected-path-checked disk DB and own4448 port, verifies restart/signature/key persistence, staff denial, rate budget and idempotency.38/38 HTTP checks pass; report under test-results/kit-http-BvFMXv. Initial rate assertion incorrectly counted pre-restart attempts; corrected to the two account attempts after restart and reran. Owner data/4194 untouched.

Client gating, printable QR batch UI and offline receipt verification are the next milestone. This is a client access deterrent, **not unbreakable DRM**: a local fitter necessarily has the sequence in process memory and determined users can modify the app. Stronger optional server generation should accept a source/recipe, keep the executable sequence server-side and release it only after unlock. No photo upload/server generation is currently performed or claimed. Free local generation/preview must remain available without accounts/credits.
