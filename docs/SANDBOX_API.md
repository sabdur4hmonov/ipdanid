# Local commerce sandbox

This API implements local transactional behavior, not live merchant integrations. It refuses NODE_ENV=production. Development catalog values are examples, not an offer to sell. Account & shop now connects browser and native customer flows. Photo generation remains local/free; original photos are never uploaded.

Run with Node 24 and `npm run local` for website4183 + API4311, or `npm run server` for the API alone. It binds loopback. LOCAL_ADMIN_TOKEN, CODE_PEPPER and SANDBOX_PAYMENT_KEY may be independent environment values of at least32 characters. Otherwise generated values persist in ignored `tmp/data/local-secrets.json`; keep this file with the database backup and never commit it. An incomplete existing file refuses startup rather than silently breaking old tokens. No permanent default administrator credentials exist. The administration tab accepts the local admin token in memory only; root bearer protection is not full production role separation.

Migration004 adds salted scrypt account credentials, rotating hashed recovery keys, support replies and optimistic product revisions (stock mutations invalidate stale catalog edits). Account registration upgrades the current guest while preserving its ownership/credits and revokes previous sessions. Login returns a7-day session. Recovery requires the one-time key, rotates it and revokes all sessions; no email-delivery claim. The UI shows this key once and persists only the selected session fields.

- GET /api/account; POST /api/account/register, /login, /recover, /logout.
- GET /api/orders; POST /api/orders/:id/return. Idempotent order retry rejects changed items/address. Returns/refunds are local state only; spent order credits block automatic refund for manual resolution.
- GET /api/instructions and /api/instructions/:id/progress. Explicit uploads preserve exact immutable instructions; different owners have independent server records. Explicit progress push uses expectedRevision and exact sequence hash. Pull is a deliberate local change.
- GET /api/support includes owner-only tickets and reply bodies without private admin identity.
- Protected GET /api/admin/products, /orders, /support, /codes, /audit; POST /api/admin/products with expectedRevision; /api/admin/codes/revoke; /api/admin/support/:id/reply; /api/admin/orders/:id/test-payment, /fulfill, /refund. All money/fulfillment events are explicitly sandbox operations.

Browser requests use same-origin /api through the Vite proxy. Native CapacitorHttp uses loopback4311 with adb reverse; browser mixed-content workarounds are unnecessary. Debug-only Android network security permits127.0.0.1; release source remains restrictive. Authentication errors, offline failure, credit shortage and revision conflicts are visible in UZ/RU/EN. Read/write budgets are600/120 per loopback IP per minute; credential attempts12. Tests use separate4321/4322 databases/ports.

- GET /api/catalog and /api/health: explicitly labeled sandbox/development data.
- POST /api/session: opaque guest bearer token, seven-day expiry.
- POST /api/orders: {items:[{productId,quantity}],address:{name,city,street},requestKey}. Price and stock are server authoritative; UZS amount is whole sums in this sandbox. Shipping/discounts/COD still need configured policies.
- GET /api/orders/:id and POST /api/orders/:id/cancel: ownership enforced; pending stock restores once.
- POST /api/admin/codes: admin bearer; {profile,quota,expiresAt}. Secure readable code is returned once; only HMAC is stored. Redeem at POST /api/codes/redeem {code}; duplicate retry is free.
- POST /api/admin/sandbox/sign: admin only; {event:{eventId,orderId,amountMinor,currency:"UZS",status:"paid",timestamp}} produces exact raw + signature. POST exact raw to /api/sandbox/callback with X-Sandbox-Signature. This is a synthetic payment event and never evidence of real payment. Signature, amount, age, event uniqueness and order transition enforced.
- GET /api/credits; POST /api/jobs/reserve {requestKey,sequenceHash}; POST /api/jobs/finish {jobId,instruction|null}. Null refunds a failure; validated successful instructions remain downloadable at GET /api/instructions/:id without another charge. This is entitlement storage, not a replacement server algorithm.
- POST /api/gifts {credits,expiresAt,requestKey}: transfers existing sandbox credits into a gift reservation; idempotent request retries return the same secure claim token while active. No purchase or message is implied. POST /api/gifts/redeem {claimToken}: one recipient only, free duplicate retry. POST /api/gifts/:id/cancel: buyer-only refund of an unclaimed gift. Expired gifts refund once during cleanup. Tokens are never stored in plaintext or audit logs.
- POST /api/instructions/:id/progress {progress,expectedRevision}: compare-and-swap conflict; stale state never overwrites newer state.
- POST /api/support {subject,body,orderId?}: ownership-linked local ticket. No emails sent.
- POST /api/admin/messages: records queued messages as sandbox_recorded, never sent. Real delivery/retries/templates pending.

Migration002 expires abandoned reservations after ten minutes and prevents another debit for an already reserved/successful sequence. Failed validation refunds the reservation. Migration003 implements gift reservations, one-recipient redemption, cancellation and expiry refunds. Migration001 provides the full initial entity vocabulary. Gift reserve/claim/cancel, order tracking/return and basic administration now have connected UI. Paid gift purchase/delivery, shipping policies, moderation, partners, media TTL, promotions and full administrative roles remain pending. SQLite BEGIN IMMEDIATE + foreign keys/unique constraints protect state. Tests cover stock rollback/revisions, ownership, code/gift retries, signed callbacks/replay, account recovery/revocation, quota refund/download, support replies and progress conflicts.

Provider adapters for Click/Payme must be implemented from selected current official merchant protocols. No generic sandbox callback is called Click/Payme. Production requires auth/identity/retention/cleanup/backups, provider credentials, policies, operational UI and owner's publication approval.
